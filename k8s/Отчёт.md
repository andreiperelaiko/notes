# Отчёт: запуск сервиса заметок в Kubernetes (minikube)

Приложение — сервис заметок из прошлого задания: фронтенд (nginx + HTML/JS), бэкенд (FastAPI)
и PostgreSQL. Здесь оно запускается в одноузловом кластере minikube.

## Окружение

| Компонент | Версия |
|---|---|
| ОС | Ubuntu 24.04 (сервер, 4 CPU, 8 ГБ RAM) |
| Docker Engine | 29.9.1 |
| minikube | 1.39.0, драйвер `docker`, рантайм `docker` |
| Kubernetes | 1.37.0 |
| kubectl | 1.37.1 |

## Состав архива

```
Отчёт.md                    этот отчёт
screencast.mov              запись экрана с демонстрацией
k8s/                        манифесты Kubernetes
  00-namespace.yaml         Namespace notes
  01-config.yaml            ConfigMap + Secret
  02-postgres.yaml          StatefulSet + headless Service для PostgreSQL
  03-migrate-job.yaml       Job: создание схемы БД
  04-backend.yaml           Deployment + Service бэкенда
  05-frontend.yaml          Deployment + NodePort Service фронтенда
backend/                    исходники и Dockerfile бэкенда
frontend/                   исходники, конфиг nginx и Dockerfile фронтенда
```

## Сборка образов и развёртывание

```bash
# 1. Кластер. Рантайм docker нужен, чтобы работал minikube docker-env
minikube start --driver=docker --container-runtime=docker --cpus=2 --memory=3072

# 2. Собираем образы сразу в Docker-демоне внутри minikube
eval $(minikube docker-env)
docker build -t notes-backend:1.0.0 ./backend
docker build -t notes-frontend:1.0.0 ./frontend

#    Другой способ: собрать обычным Docker и загрузить образ в minikube
eval $(minikube docker-env -u)
docker build -t notes-backend:1.0.0 ./backend && minikube image load notes-backend:1.0.0
docker build -t notes-frontend:1.0.0 ./frontend && minikube image load notes-frontend:1.0.0

# 3. Разворачиваем всё приложение
kubectl apply -f k8s/
kubectl get pods -n notes

# 4. Масштабируем бэкенд
kubectl scale deployment/backend -n notes --replicas=3

# 5. Открываем интерфейс
minikube service frontend -n notes --url        # http://<minikube ip>:30080
```

В манифестах указано `imagePullPolicy: IfNotPresent`. Поэтому Kubernetes берёт локально собранный образ и не пытается скачать его из Docker Hub.

## Какие абстракции Kubernetes использованы

| Абстракция | Объект | Зачем |
|---|---|---|
| **Namespace** | `notes` | Все ресурсы приложения лежат отдельно от системных. Удалить всё разом можно командой `kubectl delete namespace notes`. |
| **ConfigMap** | `notes-config` | Несекретная конфигурация: порт бэкенда (`PORT`), порт nginx (`NGINX_PORT`), адрес бэкенда для nginx (`BACKEND_URL`). |
| **Secret** | `notes-secret` | Логин и пароль PostgreSQL и строка подключения `DATABASE_URL`. Значения учебные; в настоящем кластере секреты не хранят в git. |
| **StatefulSet** | `postgres` | Для БД, потому что ей нужно состояние. У пода стабильное имя `postgres-0`, а его диск переживает перезапуск. |
| **PersistentVolumeClaim** | `data-postgres-0` | Создаётся из `volumeClaimTemplates` StatefulSet'а и получает том 1 ГиБ у StorageClass `standard` (provisioner minikube). Данные БД лежат на нём. |
| **Service (headless)** | `postgres` | `clusterIP: None`. DNS-имя `postgres` указывает прямо на под БД. Используется вместе со StatefulSet. |
| **Job** | `migrate` | Разовая задача: создаёт таблицу `notes` (`python migrate.py`) и завершается со статусом `Completed`. Запускается из того же образа, что и бэкенд. |
| **Deployment** | `backend`, `frontend` | Stateless-приложения. Deployment поддерживает заданное число реплик (ReplicaSet), перезапускает упавшие поды и делает rolling update. |
| **Service (ClusterIP)** | `backend` | Одно стабильное имя и IP `backend:8000` для всех реплик бэкенда. kube-proxy распределяет запросы между репликами. |
| **Service (NodePort)** | `frontend` | Открывает фронтенд снаружи кластера на порту узла `30080`. |
| **Init-контейнеры** | в `migrate` и `backend` | Задают порядок запуска. `migrate` ждёт, пока PostgreSQL начнёт принимать подключения (`pg_isready`). `backend` ждёт, пока появится таблица `notes`, то есть пока Job завершит миграцию. |
| **Probes** | у всех контейнеров | **readinessProbe:** трафик идёт только на готовые поды (`pg_isready` для БД, `GET /api/health` для бэкенда, `GET /` для nginx). **livenessProbe** у бэкенда: если процесс завис, Kubernetes перезапустит контейнер. |
| **Resources** | у всех контейнеров | Запросы и лимиты CPU и памяти, чтобы приложение не съело ресурсы узла. |

## Как сервисы взаимодействуют между собой

```
             Браузер
                │  http://<minikube ip>:30080
                ▼
   Service frontend (NodePort 30080)
                │
                ▼
   Pod frontend (nginx :80)
     ├─ /        → отдаёт index.html, style.css, app.js
     └─ /api/*   → proxy_pass http://backend:8000
                │
                ▼
   Service backend (ClusterIP :8000) ── балансировка kube-proxy ──┐
                │                                                 │
     ┌──────────┼──────────┐                                      │
     ▼          ▼          ▼                                      │
   Pod backend  Pod backend  Pod backend   (FastAPI :8000, ×3 после scale)
     └──────────┴──────────┘
                │  postgresql://notes:…@postgres:5432/notes
                ▼
   Service postgres (headless) → Pod postgres-0 (:5432) → PVC data-postgres-0

   Job migrate ── postgresql://…@postgres:5432 ──► создаёт таблицу notes
```

1. **Браузер → фронтенд.** Пользователь открывает `http://<minikube ip>:30080`. NodePort Service `frontend` передаёт запрос в под nginx.
2. **Фронтенд → бэкенд.** Страница вызывает API по относительному пути `/api/...`, поэтому браузер ходит на тот же адрес. nginx проксирует `/api/*` на `http://backend:8000`.
   - Имя `backend` резолвит DNS кластера (CoreDNS) в ClusterIP сервиса `backend`.
   - Адрес не зашит в образ: он приходит из ConfigMap (`BACKEND_URL`) и подставляется в конфиг nginx при старте контейнера.
3. **Балансировка.** ClusterIP Service `backend` распределяет запросы между всеми готовыми репликами. После `kubectl scale --replicas=3` новые поды автоматически попадают в Endpoints сервиса, перезапускать nginx не нужно.
   - Бэкенд добавляет в каждый ответ заголовок `X-Instance` с именем пода, по нему видно, какая реплика ответила.
   - На 12 запросах ответили все три: 8 / 3 / 1.
4. **Бэкенд → PostgreSQL.** Каждая реплика подключается по `DATABASE_URL` из Secret к хосту `postgres:5432`. Headless Service `postgres` указывает прямо на под `postgres-0`.
   - Бэкенд не хранит состояния, поэтому все реплики видят одни и те же данные.
5. **Миграция.** Job `migrate` подключается к той же БД, создаёт таблицу и завершается.
   - Init-контейнер бэкенда не пускает его в работу, пока таблицы нет. Поэтому порядок `postgres → migrate → backend` соблюдается, хотя всё применяется одной командой `kubectl apply -f k8s/`.

## Проверка

- После `kubectl apply -f k8s/` за ~25 секунд:
  - `postgres-0`, `backend` и `frontend` в статусе `Running`;
  - Job `migrate` в статусе `Completed`;
  - PVC `data-postgres-0` в статусе `Bound`;
  - перезапусков нет.
- В логах init-контейнера бэкенда видно ожидание схемы (`waiting for schema`), в логах Job — `schema is up to date`.
- Через NodePort работают все операции: `GET /` → 200, `POST /api/notes` → 201.
- `kubectl scale deployment/backend --replicas=3` поднимает три реплики, и запросы через Service доходят до каждой (видно по `X-Instance`).
- После `kubectl delete pod postgres-0` StatefulSet пересоздаёт под с тем же PVC, и заметки остаются на месте.
- В интерфейсе, открытом через minikube, создаются и отображаются заметки.
