# Отчёт: сервис заметок

## 1. Доменная область

Сервис личных заметок. Пользователь может создать заметку (заголовок и текст),
посмотреть список заметок, найти заметку поиском, отредактировать её и удалить.

## 2. Стек

| Часть | Технологии |
|---|---|
| Фронтенд | HTML + CSS + JavaScript без фреймворков и сборки (`index.html`, `style.css`, `app.js`), раздаёт **nginx** |
| Бэкенд | **Python 3.12**, **FastAPI**, сервер **Uvicorn** |
| Доступ к БД | **psycopg 3**, обычные SQL-запросы |
| СУБД | **PostgreSQL 16** |
| Запуск | **Docker Compose** |

Как устроено:

```
Браузер → frontend (nginx :80) ── /       → index.html
                               └─ /api/*  → backend (FastAPI :8000) → db (PostgreSQL)
migrate (разовый процесс) → db
```

Фронтенд обращается к API по относительному пути `/api/...`. nginx отдаёт страницу и перенаправляет `/api` на бэкенд.

## 3. Сущности

Одна сущность — **заметка** (таблица `notes`):

| Поле | Тип | Описание |
|---|---|---|
| `id` | SERIAL, первичный ключ | идентификатор |
| `title` | VARCHAR(200), обязательное | заголовок |
| `content` | TEXT | текст |
| `created_at` | TIMESTAMPTZ | когда создана |
| `updated_at` | TIMESTAMPTZ | когда изменена |

CRUD-операции:

| Операция | HTTP |
|---|---|
| Create | `POST /api/notes` |
| Read | `GET /api/notes`, `GET /api/notes/{id}` |
| Update | `PUT /api/notes/{id}` |
| Delete | `DELETE /api/notes/{id}` |

## 4. Соответствие 12 факторам

### I. Кодовая база
Весь код лежит в одном git-репозитории. Из него разворачиваются любые окружения
(локальное, тестовое, продакшен), они отличаются только переменными окружения.

### II. Зависимости
Зависимости бэкенда явно перечислены с точными версиями в `backend/requirements.txt`
и устанавливаются внутрь Docker-образа. На системные пакеты приложение не полагается
(драйвер PostgreSQL ставится как `psycopg[binary]`). Версии базовых образов зафиксированы.

### III. Конфигурация
Настройки читаются из переменных окружения:
- бэкенд: `DATABASE_URL` (подключение к БД), `PORT`;
- фронтенд: `BACKEND_URL` (куда проксировать `/api`), `NGINX_PORT`. Они подставляются в конфиг nginx при старте контейнера.

В коде нет паролей и адресов. Локальные значения лежат в файле `.env`, он не попадает в git.
В репозитории есть только шаблон `.env.example`.

### IV. Сторонние службы
PostgreSQL подключается по адресу из `DATABASE_URL`. Чтобы заменить локальную БД на облачную,
достаточно поменять переменную, код не трогается.

### V. Сборка, релиз, выполнение
- **Сборка:** `docker compose build` создаёт образы из кода и зависимостей.
- **Релиз:** образ плюс переменные окружения (`.env`).
- **Выполнение:** `docker compose up` запускает контейнеры из готовых образов.

Код внутри работающего контейнера не меняется: чтобы изменить код, нужно пересобрать образ.

### VI. Процессы
Бэкенд не хранит состояние в памяти между запросами: все данные лежат в PostgreSQL.
На каждый запрос открывается соединение с БД, после запроса оно закрывается.
Поэтому экземпляр бэкенда можно перезапустить или запустить несколько копий без потери данных.

### VII. Привязка портов
Бэкенд сам запускает HTTP-сервер (Uvicorn) и слушает порт из переменной `PORT`.
Внешний веб-сервер ему не нужен. nginx тоже слушает свой порт (`NGINX_PORT`).

### VIII. Параллелизм
Бэкенд масштабируется запуском нескольких экземпляров:

```bash
docker compose up --scale backend=3
```

Экземпляры не хранят состояния, поэтому запрос может обработать любой из них.
Чтобы было видно, какой экземпляр ответил, в каждый ответ добавляется заголовок `X-Instance` с именем контейнера.

### IX. Утилизируемость
Бэкенд стартует меньше чем за секунду. По сигналу `SIGTERM` Uvicorn перестаёт принимать новые
запросы, дожидается текущих и завершается. В Dockerfile запуск идёт через `exec`, поэтому
сигнал получает сам Uvicorn. Если процесс убить внезапно, незавершённая транзакция в PostgreSQL
откатится, и данные останутся целыми.

### X. Паритет разработки и эксплуатации
В разработке используются та же СУБД (PostgreSQL 16), те же Docker-образы и тот же
`docker-compose.yml`, что и при эксплуатации. Отличаются только значения переменных окружения.

### XI. Журналирование
Приложение не пишет логи в файлы, а выводит их в стандартный поток вывода (stdout/stderr).
Это делают Uvicorn (журнал запросов) и nginx. Сбором логов занимается окружение,
например `docker compose logs backend`.

### XII. Задачи администрирования
Создание схемы БД — разовый процесс `python migrate.py`. Он запускается из того же образа и с тем же
`DATABASE_URL`, что и бэкенд. В compose это отдельный сервис `migrate`: он выполняется перед стартом
бэкенда и завершается. Повторный запуск безопасен, потому что используется `CREATE TABLE IF NOT EXISTS`.
