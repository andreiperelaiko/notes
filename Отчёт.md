# Отчёт: сервис заметок «Notes Service»

## 1. Доменная область

Приложение — персональный сервис заметок (упрощённый аналог Google Keep / Apple Notes).
Пользователь может:

- создавать, просматривать, редактировать и удалять заметки;
- группировать заметки по блокнотам (папкам), переименовывать и удалять блокноты;
- закреплять важные заметки — они показываются в начале списка;
- искать заметки по подстроке в заголовке и тексте;
- фильтровать заметки по блокноту или смотреть заметки без блокнота.

## 2. Стек реализации

| Слой | Технологии |
|---|---|
| Фронтенд | HTML + CSS + JavaScript без фреймворков и сборки (SPA на `fetch`), раздаётся **nginx 1.27** |
| Бэкенд | **Python 3.12**, **FastAPI** (REST, HTTP/1.1), **Uvicorn** (ASGI-сервер), **Pydantic v2** (валидация) |
| Доступ к БД | **psycopg 3** + **psycopg-pool** (пул соединений), «сырой» SQL без ORM |
| СУБД | **PostgreSQL 16** |
| Миграции | собственный минимальный мигратор: SQL-файлы `backend/migrations/*.sql` + таблица `schema_migrations` |
| Окружение | **Docker**, **Docker Compose** |

Стек нетяжёлый: образ бэкенда — `python:3.12-slim`, фронтенд — `nginx:alpine`, БД — `postgres:16-alpine`;
нет ни сборки фронтенда (Node.js не нужен), ни тяжёлых фреймворков.

### Архитектура

```
 Браузер ──HTTP──► frontend (nginx :80)
                     ├── /        → статика (index.html, app.js, style.css)
                     └── /api/*   → proxy_pass ──► backend (FastAPI :8000) ×N
                                                       │
                                                       ▼
                                                 db (PostgreSQL :5432)
 migrate (разовый процесс: python -m app.migrate) ──────┘
```

Фронтенд и API доступны пользователю с одного origin (nginx проксирует `/api`), поэтому CORS не нужен.

### Структура репозитория

```
backend/
  app/
    __main__.py      точка входа: запуск uvicorn на $PORT
    main.py          FastAPI-приложение, middleware логирования, /api/health
    config.py        чтение конфигурации из переменных окружения
    db.py            пул соединений к PostgreSQL
    logging_setup.py JSON-логи в stdout
    migrate.py       админ-процесс применения миграций
    schemas.py       Pydantic-модели запросов и ответов
    routers/notebooks.py, routers/notes.py   CRUD-эндпоинты
  migrations/001_init.sql
  requirements.txt, Dockerfile
frontend/
  public/            index.html, app.js, style.css
  nginx/default.conf.template
  Dockerfile
docker-compose.yml, .env.example, README.md
```

## 3. Основные сущности

### Блокнот (`notebooks`)

| Поле | Тип | Описание |
|---|---|---|
| `id` | BIGSERIAL, PK | идентификатор |
| `name` | VARCHAR(100), NOT NULL, UNIQUE | название |
| `created_at` | TIMESTAMPTZ | дата создания |

В API ответ дополнительно содержит вычисляемое поле `notes_count` — число заметок в блокноте.

### Заметка (`notes`)

| Поле | Тип | Описание |
|---|---|---|
| `id` | BIGSERIAL, PK | идентификатор |
| `title` | VARCHAR(200), NOT NULL | заголовок |
| `content` | TEXT, NOT NULL | текст |
| `notebook_id` | BIGINT, FK → `notebooks.id`, `ON DELETE SET NULL`, nullable | блокнот |
| `pinned` | BOOLEAN | закреплена ли заметка |
| `created_at`, `updated_at` | TIMESTAMPTZ | даты создания и последнего изменения |

Связь: блокнот 1 — N заметок. Заметка может быть без блокнота; при удалении блокнота заметки не теряются,
а становятся «без блокнота».

### CRUD-операции

| Сущность | Create | Read | Update | Delete |
|---|---|---|---|---|
| Блокнот | `POST /api/notebooks` | `GET /api/notebooks`, `GET /api/notebooks/{id}` | `PUT /api/notebooks/{id}` | `DELETE /api/notebooks/{id}` |
| Заметка | `POST /api/notes` | `GET /api/notes` (фильтры, поиск, пагинация), `GET /api/notes/{id}` | `PATCH /api/notes/{id}` | `DELETE /api/notes/{id}` |

Обработка ошибок: 404 — объект не найден, 409 — блокнот с таким именем уже есть,
422 — невалидные данные или ссылка на несуществующий блокнот.

## 4. Соответствие методологии 12 факторов

### I. Кодовая база — одна кодовая база под контролем версий, много развёртываний

Весь код (бэкенд, фронтенд, миграции, Dockerfile-ы, compose) лежит в одном git-репозитории.
Из этой кодовой базы собираются одни и те же образы, которые разворачиваются в разных окружениях
(локально, на стенде, в проде); окружения отличаются только конфигурацией.
Фронтенд и бэкенд — два процесса одного приложения, у них общий релизный цикл,
поэтому монорепозиторий здесь уместен: это одно приложение, а не два разных.

### II. Зависимости — явно объявлены и изолированы

- Python-зависимости объявлены в `backend/requirements.txt` с точными версиями (`==`).
- Зависимости устанавливаются в изолированное окружение: в Docker — в образ, при локальной разработке — в `venv`.
- Приложение не полагается на системные утилиты: драйвер PostgreSQL ставится как `psycopg[binary]`,
  `psql` или `libpq` из системы не нужны. Healthcheck в Dockerfile использует сам Python, без `curl`.
- Базовые образы закреплены по версии (`python:3.12-slim`, `nginx:1.27-alpine`, `postgres:16-alpine`).
- У фронтенда нет внешних зависимостей: только браузерный JS, без CDN.

### III. Конфигурация — хранится в окружении

Всё, что меняется между окружениями, читается из переменных окружения (`backend/app/config.py`):
`DATABASE_URL`, `PORT`, `HOST`, `LOG_LEVEL`, `DB_POOL_*`, `CORS_ORIGINS`.
В коде нет ни паролей, ни адресов, ни отдельных конфигов под окружения (`config_prod.py` и т. п.).
Обязательный `DATABASE_URL` проверяется при старте: без него процесс сразу падает с понятной ошибкой.

Фронтенд тоже конфигурируется окружением: адрес бэкенда (`BACKEND_URL`) и порт (`NGINX_PORT`)
подставляются в шаблон nginx через `envsubst` при старте контейнера, а не зашиваются в образ.
Поэтому один и тот же образ фронтенда работает с любым адресом бэкенда.

Значения для локального запуска лежат в `.env` (он в `.gitignore`). В репозитории есть только шаблон `.env.example`.
Проверка из методологии выполняется: репозиторий можно хоть сейчас открыть публично, не скомпрометировав ни одного секрета.

### IV. Сторонние службы — подключаемые ресурсы

PostgreSQL — подключаемый ресурс, который задаётся одной строкой `DATABASE_URL`.
Для приложения нет разницы между локальным контейнером `db` и управляемой облачной БД
(Yandex Managed PostgreSQL, RDS и т. п.): чтобы заменить базу, достаточно поменять переменную, код не трогается.
Бэкенд для фронтенда тоже подключаемый ресурс, он задаётся через `BACKEND_URL`.

### V. Сборка, релиз, выполнение — строго разделены

- **Сборка** — `docker compose build` (или `docker build`): из кода и зависимостей получается
  неизменяемый образ `notes-backend:<APP_VERSION>` / `notes-frontend:<APP_VERSION>`.
  Во время сборки конфигурация не используется.
- **Релиз** — образ конкретной версии плюс конфигурация окружения (`.env` / переменные оркестратора).
  Версия задаётся через `APP_VERSION`, и любой релиз можно воспроизвести или откатить, указав прежний тег.
- **Выполнение** — `docker compose up`: запуск процессов из готового релиза.
  В рантайме код не меняется: внутри контейнера нет исходников для правки, процесс работает
  от непривилегированного пользователя, а изменение кода требует новой сборки.

Миграции БД — отдельный шаг (сервис `migrate`), а не побочный эффект старта приложения.

### VI. Процессы — приложение выполняется как один или несколько процессов без состояния

Бэкенд не хранит состояние между запросами: ни сессий в памяти, ни локальных файлов,
ни кэшей, без которых нельзя обойтись. Всё долговременное состояние лежит в PostgreSQL.
Каждый запрос берёт соединение из пула и выполняется в собственной транзакции.
Поэтому любой запрос может обработать любой экземпляр бэкенда, «липкие сессии» не нужны,
а экземпляр можно перезапустить или убить без потери данных.
Состояние фронтенда (выбранный блокнот, открытая заметка) живёт только в браузере.

### VII. Привязка портов — сервис экспортируется через привязку к порту

Бэкенд самодостаточен: он сам поднимает HTTP-сервер (Uvicorn встроен как библиотека,
`python -m app`) и слушает порт из `$PORT`. Внешний сервер приложений (Apache/mod_wsgi и т. п.) не нужен.
Фронтенд-контейнер тоже экспортирует HTTP через порт (`NGINX_PORT`), а наружу публикуется `FRONTEND_PORT`.
Значит, бэкенд может служить подключаемым ресурсом для другого сервиса, в нашем случае для nginx.

### VIII. Параллелизм — масштабирование через процессную модель

Нагрузка масштабируется горизонтально, запуском дополнительных процессов-экземпляров:

```bash
docker compose up -d --scale backend=3
```

Бэкенд не хранит состояния (фактор VI) и не публикует фиксированный порт на хост, поэтому экземпляры не конфликтуют.
nginx обращается к имени `backend`, которое DNS Docker раскрывает во все экземпляры.
Каждый ответ содержит заголовок `X-Instance` (hostname контейнера), по нему видно, какой экземпляр обработал запрос.
Это пригодится в задании про балансировку.
Типы процессов разделены: `web` (backend), `frontend` (nginx), разовый `migrate`.
Процессы не демонизируются и не пишут PID-файлы: жизненным циклом управляет Docker.

> Ограничение: nginx разрешает имя `backend` при старте. Если масштабировать бэкенд после запуска nginx,
> фронтенд нужно перезапустить (`docker compose restart frontend`). Полноценная балансировка будет
> настроена в следующих заданиях.

### IX. Утилизируемость — быстрый запуск и корректное завершение

- **Быстрый старт:** процесс бэкенда стартует меньше чем за секунду (открывает пул и начинает слушать порт), тяжёлой инициализации нет.
- **Graceful shutdown:** по `SIGTERM` Uvicorn перестаёт принимать новые соединения, дожидается текущих запросов
  (не дольше `timeout_graceful_shutdown=10` с), после чего lifespan-обработчик закрывает пул соединений к БД.
  В Dockerfile `CMD` записан в exec-форме, поэтому Python — PID 1 и сигнал получает сам, без shell-обёртки.
  Проверено: после `SIGTERM` процесс корректно завершается примерно за 0.1 с, в логе есть `Shutting down` → `stopped` → `Finished server process`.
- **Устойчивость к внезапной смерти:** каждый запрос выполняется в транзакции. Если процесс убит посреди запроса,
  PostgreSQL откатит незавершённую транзакцию, и данные останутся консистентными.
  Мигратор применяет каждую миграцию в отдельной транзакции и берёт advisory lock,
  поэтому прерванный или параллельный запуск безопасен.

### X. Паритет разработки и эксплуатации — окружения максимально похожи

- В разработке используется та же СУБД той же версии (PostgreSQL 16), что и в эксплуатации.
  SQLite или in-memory заглушки «для удобства» не используются.
- Локально приложение запускается теми же Docker-образами и тем же `docker-compose.yml`,
  отличаются только значения переменных окружения.
- Миграции применяются одинаково во всех окружениях одной командой `python -m app.migrate`.
- Путь от изменения кода до развёртывания короткий: пересобрать образ и перезапустить контейнер.

### XI. Журналирование — логи как поток событий

Приложение не пишет логи в файлы и не занимается их ротацией. Каждое событие —
одна строка JSON в `stdout` (`backend/app/logging_setup.py`): время, уровень, логгер, сообщение и поля
(метод, путь, статус, длительность запроса). Например:

```json
{"ts": "2026-10-14T14:08:52.818216+00:00", "level": "INFO", "logger": "notes", "msg": "request", "method": "POST", "path": "/api/notes", "status": 201, "duration_ms": 1.8}
```

Сбор, хранение и маршрутизация логов — задача окружения: `docker compose logs`, драйвер логов Docker
или внешний агрегатор (ELK, Loki и т. п.), без изменений в коде. Структурированный формат удобно парсить.
nginx в официальном образе тоже пишет access/error-логи в stdout/stderr.

### XII. Задачи администрирования — разовые процессы

Административная задача (миграция схемы БД) — разовый процесс `python -m app.migrate`.
Он запускается в том же окружении, что и приложение: тот же образ, тот же код, та же конфигурация (`DATABASE_URL`):

```bash
docker compose run --rm migrate
```

Код миграций (`backend/migrations/*.sql` и `app/migrate.py`) поставляется вместе с кодом приложения
и версионируется в том же репозитории, поэтому схема БД всегда соответствует версии кода.
В compose сервис `migrate` выполняется перед стартом бэкенда (`depends_on: service_completed_successfully`).
Миграции идемпотентны: уже применённые версии хранятся в `schema_migrations`, повторный запуск ничего не меняет.

## 5. Проверка работоспособности

Проверено вручную:

1. Миграции применяются на чистой БД, повторный запуск ничего не делает (`applied: 0`).
2. Все CRUD-операции API отрабатывают с ожидаемыми кодами: 201/200/204, 404 на несуществующий объект,
   409 на дублирующееся имя блокнота, 422 на пустой заголовок или несуществующий блокнот.
   При удалении блокнота заметки остаются, их `notebook_id` становится `null`.
3. Через UI создаются блокнот и заметка в нём, работают сохранение, поиск и фильтр.
4. Graceful shutdown по `SIGTERM` и fail-fast при занятом порту.
